# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal web app (in English) for practicing Japanese vocabulary: it shows a word, the user types the reading in romaji, and the app checks it. Svelte 5 + Vite + TypeScript + wanakana, data only in localStorage (no backend).

## Commands

```bash
npm run dev      # development server
npm test         # vitest run (all tests)
npx vitest run src/core/romaji.test.ts -t "macron"   # one file / one test by name
npm run check    # svelte-check (tsconfig.app.json) + tsc (tsconfig.node.json)
npm run build    # production build into dist/
```

No linter is configured. Tests live next to the module they cover (`*.test.ts` in `src/core/` and `src/data/`); the `.svelte` components have none, so UI changes are checked in the browser. Vitest ignores `.claude/` (old worktrees carry their own copies of the tests).

## Architecture

Source layout (each folder has its own README): `src/core/` (pure logic: types, romaji, kana), `src/data/` (words, stats, practice session and modes, stats rows, storage, io, anki), `src/components/{practice,stats,manage}/` (Svelte UI). Dependencies point downwards: components → data → core. Names for the practice flow (practice session, practice mode, pool) are in [GLOSSARY.md](GLOSSARY.md).

- [src/App.svelte](src/App.svelte) owns the `words` state (`$state`) and persists it with an `$effect` that calls `saveWords($state.snapshot(words))`. `WordPractice` receives `words`; `Manage` (`bind:words`) does the CRUD and import/export. Any change to the pool is saved automatically; do not call `saveWords` in components.
- [src/data/storage.ts](src/data/storage.ts) is the **only** access point to localStorage (keys `zennia:words` with format `{ version: 2, words }`, `zennia:stats` and `zennia:kana-selection`). Swapping for IndexedDB/a backend should touch only this file, in particular its private `load` and `save` helpers, which hold the failure rules: anything missing, unreadable or invalid gives the fallback, and a full or blocked storage is ignored. Reads go through the sanitizers. Words and stats are persisted by `App.svelte`; the kana selection is the exception, saved by `KanaPractice` itself.
- [src/data/words.ts](src/data/words.ts): the rules of the word pool. `sanitizeWords` validates any external data (localStorage or imported file; accepts an array or `{ words }`, discards items without `japanese`/`hiragana`, regenerates duplicate ids, and always sets `disabled` to a boolean, `false` when missing). `mergeWords` deduplicates by id or by `japanese|hiragana`. `validateWord`, `makeWord` and `updateWord` take the form texts (`WordFields`, as typed; they trim). Tags (see the glossary) are `Word.tags`, always stored as a clean list: `sanitizeWords` reads them (missing = none, so version 1 files still import), `mergeWords` unites them, and `validateTag`, `cleanTags`, `sameTag`, `allTags`, `addTag`, `removeTag`, `renameTag` (merges into an existing tag), `deleteTag` and `filterByTags` (every chosen tag) hold the rules; they never affect the practice pool. `tagHue` gives each tag its pastel colour. In Settings, `Manage` has a Tags section (rename, merge or remove a tag everywhere), shows each word's tags as clickable [TagChip](src/components/manage/TagChip.svelte)s that filter the list (the active filter sits under the search, with an X) and a bulk button to add / remove a tag on the selection, with [TagInput](src/components/manage/TagInput.svelte) in the forms. `searchWords` matches the word, reading, romaji or meaning; `sortWords` orders the list; `importSummary` builds the message shown after an import. `Manage` calls these and keeps only screen state.
- [src/data/io.ts](src/data/io.ts): JSON export/import of words and of stats (with `version` for migrations), the export file names (`exportFilename`, `statsExportFilename`) and browser download.
- [src/data/anki.ts](src/data/anki.ts): imports an Anki "Notes in Plain Text" export (tab-separated, quoted multi-line HTML fields, only front + back per card). Word = front text; reading = the back's headword with each `<ruby>` replaced by its `<rt>` furigana (kana-only words are their own reading); meaning = the first nested `<div>` on the back. Cards whose reading isn't pure kana are skipped; repeated word + reading pairs are merged into one word, with different meanings joined by `; `.
- The top bar of `App.svelte` has four tabs: `Words` (`WordPractice`, the saved words), `Kana` (`KanaPractice`), `Stats` and `Settings` (the `Manage` component). `KanaPractice` (hiragana/katakana symbols from [src/core/kana.ts](src/core/kana.ts), defined in hiragana and checked with `checkAnswer`; "almost" is shown as incorrect). Which keys a click on the grid selects (`sectionKeys`, `columnKeys`, `lineKeys`, `scriptKeys`, `selectKeys`, `toggleKeys`) and the first-run selection (`defaultKanaSelection`, the basic hiragana) are pure functions in `kana.ts`; the component only restarts the session and saves the selection.
- Practice session: [src/data/practice-session.ts](src/data/practice-session.ts) holds the flow shared by both practices as pure functions on a `Session` (current item, verdict, hits/total/streak/best): `nextRound` draws (never the previous item unless it is the only one), `submit` ignores an empty answer, checks and scores, or moves on when a verdict is already shown, and `resetScore` clears the score. What differs between the practices is a `PracticeMode` (pool, key, draw weight, check, record), built by `wordsMode` and `kanaMode` in [src/data/practice-modes.ts](src/data/practice-modes.ts); the kana mode turns `almost` into incorrect. `WordPractice` and `KanaPractice` keep the typed answer, the input focus and the session in a `$state`, and render [PracticeCard](src/components/practice/PracticeCard.svelte).
- [src/data/stats.ts](src/data/stats.ts) + [src/data/stats-rows.ts](src/data/stats-rows.ts) + [src/components/stats/Stats.svelte](src/components/stats/Stats.svelte): lifetime hit/miss tallies, kept apart for the two practices. Words are tallied per word id (a wrong answer is a wrong word; the kana inside it are **not** counted). The hiragana/katakana practice is tallied per symbol with `kanaKey` (`hiragana:か` / `katakana:か`), so the two scripts stay separate. `App.svelte` owns the `stats` state and persists it under `zennia:stats` (separate from the words, not part of the words' JSON export). The Stats tab has its own export/import buttons (`exportStatsJSON`, `importStatsJSON`, `statsExportFilename` in `io.ts`; file `{ version: 1, exportedAt, stats }`): import validates with `sanitizeStats` and **replaces** the current stats after a confirmation. Word stats are keyed by word id, so import the words JSON first when moving to another domain. The practice modes call `recordAnswer` (words) and `recordKana` (kana); `almost` counts as a miss. The next word/symbol is drawn with `pickWeighted` using `drawWeight` (weight 0.5–5 from the Wilson upper bound of the miss rate, z = 1.64, so items with few answers keep a high weight until their accuracy is backed by enough data; never-answered items weigh 6 so everything gets seen first), so missed and under-sampled items come up more often and well-proven ones less, without ever disappearing; the previous item is still excluded. Both modes show a session scoreboard ([src/components/practice/Scoreboard.svelte](src/components/practice/Scoreboard.svelte)): a row of tiles below the practice card (correct, wrong, accuracy, streak, total answered), with a reset button that asks for confirmation. The Stats list is built by `buildRows` (one row per answered word or kana; words that were deleted are not listed, their stats stay saved) and `filterRows` (kinds, search, sort) in `stats-rows.ts`; `totalTally` and `accuracyLevel` (high from 80%, low under 60%) are in `stats.ts`, and the kana key is undone by `parseKanaKey` next to `kanaKey`.
- Writing sheet: in Settings, the printer button next to the selection actions opens the browser print dialog for the selected words ([PrintSheet](src/components/print/PrintSheet.svelte) renders the sheet hidden on screen and calls `window.print()`; `@media print` hides the app and shows only the sheet). Each word gets rows of A4 squares (layout in [src/core/sheet.ts](src/core/sheet.ts)): the word with numbered strokes, then faint copies to trace, then empty squares, plus a row of small squares (half the side) with the same trace-then-free idea. Stroke data is KanjiVG in `public/strokes.json` (CC BY-SA 3.0, credited on the sheet), loaded lazily by [src/data/strokes.ts](src/data/strokes.ts); characters missing from it fall back to the font glyph.
- [src/core/types.ts](src/core/types.ts): `Word { id, japanese, hiragana, meaning, disabled, tags }`, `Verdict`, `WordsFile`, `Stats`.

### Checking ([src/core/romaji.ts](src/core/romaji.ts))

The subtlest part of the project. The answer is compared **by sound, in hiragana**, not by text:

- `normalizeKana` converts to hiragana via wanakana with `convertLongVowelMark: false` and replaces `ー` with the previous vowel (wanakana by default converts `ー` to `う` in the o row, which would break `コーヒー` = `koohii`).
- `checkAnswer` expands macrons into every spelling (`ō` → `ou`/`oo`, capped at 256 candidates), accepts a final `nn` as ん and compares with the normalized hiragana → `correct`.
- If only the vowel length differs (comparison by `skeleton`), it returns `almost`, which **counts as an error**: length changes the word (おばさん/おばあさん). Do not relax this without a decision from the user.
- The displayed romaji (`toDisplayRomaji`) is always derived from the hiragana; it is **never saved** in the data model. The hiragana is entered manually (kanji do not convert reliably).

## Conventions

- Svelte 5: always use runes (`$state`, `$derived`, `$effect`), not Svelte 4 syntax. No SvelteKit.
- Code, comments and UI text in English.
- Commit messages in English, following Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`...).
- The interface is provisional (simple, scoped CSS); functionality is the priority.
- Deploy planned on Vercel (Vite detected automatically). localStorage is per domain, so changing the URL requires exporting/importing the JSON.
- After making a change, make sure `npm run dev` is running (start it in the background if not) **from the directory where the change was made**, so that a worktree serves its own code rather than `main`'s. Vite picks the next free port when 5173 is taken, so report the URL it prints. The user tests changes in the browser.
- Before making any change, sync with `main` to avoid conflicts: run `git pull` (on `main`), or on a feature branch/worktree run `git fetch origin` and merge `origin/main` into it.
